# SD-card read benchmarks, 2026-11-25

Purpose: measure what the card in the ESP32-S3-CAM can actually deliver before
choosing between a multi-model SD library and an activation-driven MoE.

This was a read-only benchmark. The only write was a temporary 1 MiB file used
to test write speed; it was deleted. The card still contains the same five
entries it had before the test. The bench app was flashed to `0x10000` only;
the bootloader, partition table, model partition and card were not rewritten.
The standard `BENCH_MODE=0` image was restored afterwards and boot was verified.

## Setup

| Item | Value |
|---|---|
| Board | ESP32-S3-CAM, ESP32-S3 v0.2, 8 MB octal PSRAM, 16 MB flash |
| Card | `SK32G`, SDHC, 30,436 MB, 62,333,952 sectors |
| Bus | **1-bit** SDMMC, CLK 39 / CMD 38 / D0 40 |
| Frequencies tested | 20 MHz and 40 MHz |
| Card-reported limit | 40 MHz at 40 MHz request |
| FATFS | `CONFIG_FATFS_SECTOR_4096=y`, per-file cache on |
| Bench FATFS LFN | disabled, so the model appeared as `STORIE~1.BIN` |
| Main firmware FATFS | LFN enabled, so it sees `stories260K.bin` |
| Raw logs | `logs/sdbench_raw_2026-11-25.log`, `logs/sdbench_fatapi_2026-11-25.log` |
| Restore log | `logs/sdbench_restore_2026-11-25.log` |

The 1-bit bus is what the current wiring and firmware use. Four-bit mode was not
tested; the board/firmware only defines D0.

## Raw sector reads

These bypass FATFS and read the card directly.

| Pattern | 20 MHz | 40 MHz |
|---|---:|---:|
| Sequential, 4 KiB chunks | 1.799 MB/s | 2.823 MB/s |
| Sequential, 16 KiB chunks | 2.317 MB/s | 4.369 MB/s |
| Sequential, 32 KiB chunks | 2.435 MB/s | 4.780 MB/s |
| Sequential, 64 KiB chunks | **2.456 MB/s** | **4.865 MB/s** |
| Random 4 KiB | 2.085 MB/s, 1.97 ms | 3.625 MB/s, 1.13 ms |
| Random 9 KiB | 2.291 MB/s, 4.02 ms | 4.267 MB/s, 2.16 ms |
| Random 17 KiB | 2.385 MB/s, 7.30 ms | 4.569 MB/s, 3.81 ms |
| Random 32 KiB | 2.424 MB/s, 13.5 ms | 4.748 MB/s, 6.90 ms |
| Random 35 KiB | **2.430 MB/s, 14.75 ms** | **4.770 MB/s, 7.51 ms** |
| Random 64 KiB | 2.452 MB/s, 26.7 ms | 4.852 MB/s, 13.5 ms |
| Random 512 B | 0.994 MB/s, 0.515 ms | 1.675 MB/s, 0.306 ms |

At 20 MHz the bus is essentially at its 1-bit theoretical ceiling (~2.5 MB/s).
At 40 MHz it reaches ~4.9 MB/s, also close to the 1-bit ceiling. The card and
the board both accepted 40 MHz.

## FATFS file reads

The existing `stories260K.bin` was read through FATFS. Three access styles were
compared because the result changes the design.

| API / pattern | 1 MiB file | 275 KiB blob | Random 9 KiB | Random 17 KiB | Random 35 KiB |
|---|---:|---:|---:|---:|---:|
| `fread`, default buffer | 787 ms, 1.342 MB/s | 205 ms | 7.30 ms | 13.42 ms | 27.13 ms |
| `fread` + 64 KiB `setvbuf` | 245 ms, 4.31 MB/s | 76 ms | 26.7 ms | 26.8 ms | 27.7 ms |
| `open` + `read` | **242 ms, 4.36 MB/s** | **63 ms** | **2.79 ms** | **4.59 ms** | **8.81 ms** |

Other measurements:

- FATFS mount at 40 MHz: **~50 ms** (49.5–55.9 ms across runs)
- FATFS mount at 20 MHz: ~70 ms in the main firmware
- `fopen` + `fclose`: **121 µs** average
- Temporary 1 MiB write with `fwrite` 64 KiB chunks: **2.86 MB/s**
  (one run; not optimized, and the file was removed)

The important result is that **the default `fread` path is the bottleneck, not
the card**. With `read()` the file system reaches 4.36 MB/s sequentially and
4.07 MB/s for a 35 KiB random read, close to the raw 4.87 MB/s. A 64 KiB
`setvbuf` fixes sequential `fread`, but it makes random `fread` worse because
each `fseek` discards the read-ahead buffer.

## Read-path workarounds tried

Several plausible fixes were tested and rejected:

| Workaround | Result |
|---|---|
| 128 KiB raw chunks instead of 64 KiB | 4.911 MB/s vs 4.865 MB/s — **~1%**, not worth a larger buffer |
| 128 KiB `read()` chunks | 4.37 MB/s — same as 64 KiB |
| FATFS logical sector 512 instead of 4096 | No measurable change |
| `CONFIG_FATFS_USE_FASTSEEK=y` | No measurable change for `lseek`/`read` |
| Disable `CONFIG_FATFS_PER_FILE_CACHE` | No improvement; slightly worse default `fread` |
| Direct FatFs `f_open`/`f_read`/`f_lseek` | 4.35 MB/s sequential, 4.04 MB/s random — no better than VFS `read()` |
| 4-bit SD bus | Not available in this wiring; only D0 is defined |
| Above 40 MHz | Not attempted; the card reports a 40 MHz limit and overclocking is not a production setting |

The winning combination is therefore simple:

- **40 MHz**
- **`open`/`read()`** (or `lseek` + `read`), not default `fread`
- **64–128 KiB chunks**
- **no FATFS tuning required**

`read()` reaches 4.36 MB/s sequential and 4.08 MB/s for a 35 KiB random read,
against a raw ceiling of 4.87 MB/s.

## What this changes for the two ideas

### Multi-model library: better than expected

A prequantized 275 KiB blob can be loaded in:

```text
275 KiB at 4.37 MB/s   =  63 ms
FATFS mount at 40 MHz  =  50 ms
validation + copy      =  a few ms
------------------------------------------------
total                  ≈ 120 ms
```

A raw 1 MiB checkpoint can be read in about **242 ms** plus mount and
quantization. The current firmware, using 20 MHz and default `fread`, takes
about **1.08 s** from `SD mounted` to `model source: SD card` in the boot log,
plus parse and quantization. So the library can be noticeably faster just by
using 40 MHz and `read()`, before changing the model format.

Recommended cold-path design:

- Use **40 MHz**.
- Use **`open`/`read`**, not default `fread`, for model blobs.
- Store a **prequantized 275 KiB blob** rather than the 1 MiB fp32 checkpoint.
- Keep one active model in SRAM; use PSRAM only as staging/cache.
- Keep SD unmounted during inference; remount only to switch.
- Use a manifest, SHA-256, and a fixed-prompt logit check before activating a
  new model.

### MoE: still not viable per token from SD

One full FFN expert for one layer is **34,912 B**. At the measured 40 MHz
FATFS random rate that is **8.8 ms per expert fetch**. The 512-context forward
budget is **6.0 ms**, and the short-context forward is about **1.6 ms**.

| Case | Cost |
|---|---:|
| One 35 KiB expert, one layer | 8.8 ms |
| All 5 layers miss | ~44 ms/token |
| 90% hit per layer | ~4.4 ms/token |
| 95% hit per layer | ~2.2 ms/token |
| 99% hit per layer | ~0.44 ms/token |

With five layers, even a 90% per-layer hit rate costs about 4.4 ms/token, which
is most of the 6 ms budget. A 95–99% per-layer hit rate is needed before the
swap becomes tolerable, and at short context even 0.44 ms is a 27% overhead.

A quarter-width 9 KiB expert is cheaper (2.79 ms per miss), but that is a
different, trained architecture, not the current dense FFN.

Also, the fetch is on the critical path: standard MoE routing happens after
attention, so the expert for layer *l* is not known until layer *l*'s input is
ready. Prefetching would require routing earlier in the layer, which is an
architecture/quality trade, not just a loader change.

**Conclusion:** SD is a good cold store for model blobs. It is not a hot store
for per-token experts. A MoE, if pursued, needs experts resident in SRAM (or
streamed from PSRAM with a very high hit rate), not fetched from SD per token.

## Caveats

- One card, one board, one set of runs. The 40 MHz result should be soak-tested
  before it is treated as a production setting.
- The card is 1-bit only in this wiring; 4-bit mode could be much faster but was
  not available to test.
- Random reads used 100 iterations over the card; the exact distribution will
  depend on the card, FAT layout and file fragmentation.
- The write number is one run with default `fwrite`; it is not a write benchmark
  and was only taken to confirm the temporary test file could be created.
- The bench app had LFN disabled, so it used the 8.3 alias `STORIE~1.BIN`. The
  main firmware has LFN enabled and sees `stories260K.bin`; the data path is the
  same.
